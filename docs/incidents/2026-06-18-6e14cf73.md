## Summary

On 2026-06-18, the ecommerce-api experienced a 22% error rate on `POST /api/checkout` caused by a TOCTOU (time-of-check/time-of-use) race condition in `reserveInventory`. Concurrent checkout requests for product 7 (Ceramic Plant Pot, limited stock of 5) all read the same stock value before any decrement was committed, passed the sufficiency check, and then raced through a 50–150 ms async business-rules delay before each decremented the shared in-memory store. Stock was driven to -3, causing every subsequent product-7 checkout to fail immediately with "Insufficient stock … available -3" until the pod was restarted.

## Root cause

`reserveInventory` in `otel-demo/ecommerce/backend/src/services/inventory.js` called `await getStock(item.id)` (a 5 ms simulated async DB read) to retrieve stock, checked sufficiency, then called `await new Promise(...)` (50–150 ms business-rules delay) before finally decrementing `inventory[item.id]`. Because Node.js yields the event loop at every `await`, multiple concurrent requests each read the same stock value (5), each passed the `5 >= 2` check, each entered the 50–150 ms await, and then each decremented the same in-memory counter in turn. Stock was driven from 5 → 3 → 1 → -1 → -3. Once negative, the fast-path `currentStock < item.quantity` guard fired on every subsequent checkout with no recovery path until pod restart.

## Contributing factors

- In-memory inventory store with no atomic compare-and-swap or mutex protection
- Two event-loop yields (`await getStock` + `await setTimeout`) between the stock read and the decrement, providing a wide concurrent-interleave window
- OTel collector initialization lag (~37 s after pod start) caused the initial StockMismatchError logs to be dropped, delaying detection
- Limited stock (5 units) for product 7 amplified impact — high-volume products with stock ≥ 50 were unaffected in this window

## Detection

Automated incident watcher detected the elevated error rate at 07:05:21 UTC via a 1-minute lookback over `otel_logs`. The fingerprint `ecommerce-api|Error` crossed the 15% threshold at 22% (92 samples). A prior identical incident (PR #16) had identified the same root cause but the fix had not been applied to the running image.

## Fix

Changed `reserveInventory` in `otel-demo/ecommerce/backend/src/services/inventory.js` to:

1. Replace `await getStock(item.id)` with a synchronous read of `inventory[item.id]` directly — eliminating the first event-loop yield.
2. Move `inventory[item.id] -= item.quantity` to immediately after the sufficiency check, **before** the business-rules `await`.

Because Node.js is single-threaded, a synchronous read-check-decrement sequence cannot be interleaved by any concurrent request. Once the decrement is committed before yielding, subsequent requests see the updated stock value and the race is closed.

See PR #17 for the diff.
