## Summary

On 2026-05-19 at 21:59:35 UTC, a TOCTOU (time-of-check/time-of-use) race condition in `reserveInventory()` caused the in-memory stock for product 7 (Ceramic Plant Pot) to go negative. With only 5 units available, four concurrent checkout requests each read `stock=5`, each passed the sufficiency check, and then each decremented independently after a 50–150 ms async yield — driving inventory to -3. Every subsequent checkout for that product failed with an "Insufficient stock: available -3" error, producing a sustained 20% error rate until the fix was deployed.

## Root cause

`reserveInventory()` in `otel-demo/ecommerce/backend/src/services/inventory.js` contained a TOCTOU race:

1. An async `getStock()` call (5 ms simulated DB read) allowed multiple concurrent requests to each cache `stock=5`.
2. Each request's sufficiency check (`currentStock < item.quantity`) used that stale read — all passed.
3. A 50–150 ms `await` delay for "inventory policy validation" yielded the Node.js event loop, letting every concurrent request reach the same check/yield gap.
4. Each request then decremented `inventory[item.id]` independently: `5 → 3 → 1 → -1 → -3`.

The post-hoc `StockMismatchError` guard detected the negative value but could not undo the corruption — inventory stayed at -3 permanently, causing every subsequent checkout to fail immediately.

## Contributing factors

- Limited stock (5 units) for product 7 made the race easy to trigger under normal load.
- The 50–150 ms artificial async delay greatly widened the race window, allowing many concurrent requests to interleave.
- The stock check used a stale async read (`currentStock`) rather than the live in-memory value, compounding the problem.
- HTTP 409 responses were not marked as trace errors, so no trace-level alert fired — detection relied solely on log-based error rate.

## Detection

Detected by the automated incident watcher monitoring log-based error rate for `ecommerce-api`. Triggered at 22:00:46 UTC when the 1-minute error rate reached 20% (threshold: 15%). Fingerprint: `ecommerce-api|Error`.

## Fix

**File:** `otel-demo/ecommerce/backend/src/services/inventory.js`

Two changes eliminate the race:

1. **Live-value check:** The sufficiency check now reads `inventory[item.id]` directly (the live in-memory value) instead of the stale `currentStock` captured by the earlier async `getStock()` call.
2. **Synchronous decrement:** The `inventory[item.id] -= item.quantity` decrement is moved to immediately after the check, before any `await`. Because Node.js is single-threaded, no other request can interleave between a synchronous check and a synchronous decrement — making the operation atomic.

The async validation delay is retained but now occurs after the decrement, so it no longer creates a race window.

See PR #3 in `har-ki/claude-code-sre-handbook` and `docs/incidents/2026-05-19-6e14cf73.md`.

## Action items

- [ ] Replace the artificial async delay in `reserveInventory()` with real inventory policy logic, or remove it if it serves no purpose.
- [ ] Add an integration test that fires multiple concurrent checkout requests for a low-stock product and asserts inventory never goes negative.
- [ ] Mark HTTP 409 checkout responses as trace errors so trace-level alerting fires alongside log-based alerting.
- [ ] Consider a persistent inventory store (database with row-level locking) to replace the in-memory map for production use.

## Open questions

- Was the 50–150 ms async delay ever intentional (e.g., simulating an external policy service)? If so, it needs a proper mutex or optimistic-locking retry loop rather than the current fix.
- Are there other endpoints that read and write `inventory` without the same atomic check-then-decrement pattern?
