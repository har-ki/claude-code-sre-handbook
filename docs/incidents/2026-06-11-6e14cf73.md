## Summary

On 2026-06-11 at ~07:52 UTC, the ecommerce-api sustained a 50% error rate (590 errors out of 1180 requests in 15 minutes) caused by a TOCTOU race condition in `inventory.js`. Concurrent checkout requests all passed a stock-availability check and then each decremented the same in-memory inventory counter — driving several products to zero or below. Product 7 (Ceramic Plant Pot, initialized with only 5 units vs. 50 for all others) was hit disproportionately, accounting for 57% of all errors. Once exhausted, in-memory inventory has no restock mechanism, so the failure was sustained rather than self-healing.

## Root cause

`reserveInventory()` in `inventory.js` reads current stock via `await getStock()` (5 ms simulated DB delay), checks whether stock is sufficient, then sleeps 50–150 ms for "business logic validation", and only _then_ decrements the counter. Because Node.js yields the event loop at every `await`, multiple concurrent requests all read the same stock value, all pass the availability check, and all later decrement — driving inventory negative. The 50–150 ms window between the check and the decrement was the primary TOCTOU exposure. Product 7's initial stock of 5 (vs. 50 for all other products) meant concurrent requests for quantity 2 exhausted it almost immediately.

## Contributing factors

- The 50–150 ms async delay between the stock check and the stock decrement created a wide TOCTOU window.
- Product 7 (Ceramic Plant Pot) was initialized with only 5 units, making it the first product to exhaust, contributing 57% of all errors.
- The load generator produced sustained concurrent traffic that reliably exercised the race window.
- Once in-memory inventory reaches 0 or below, there is no restock path, so errors do not self-heal.

## Detection

Automated incident watcher detected error rate at 50% against a 15% threshold. All errors shared the same log message pattern (`Insufficient stock for product N`) and HTTP status 409. OTel trace attribute `stock_before: 0` and negative available-stock values in span messages confirmed the race.

## Fix

Moved `inventory[item.id] -= item.quantity` from _after_ the 50–150 ms async sleep to _before_ it in `otel-demo/ecommerce/backend/src/services/inventory.js`. This ensures the decrement is performed in the same synchronous execution block as the availability check — before any event-loop yield — closing the TOCTOU window. See PR #13.

## Action items

- [ ] Replace in-memory inventory with a persistent store that supports atomic compare-and-decrement (e.g. Redis `DECRBY` with a floor check) to eliminate the residual 5 ms race window from `getStock()`.
- [ ] Restock product 7 (Ceramic Plant Pot) to parity with other products (50 units) or add a runtime restock endpoint.
- [ ] Add an integration test for concurrent checkout requests that asserts inventory never goes negative.

## Open questions

- Should `getStock()` be replaced with a synchronous read from `inventory` to fully eliminate the 5 ms race window that remains after this fix?
- Is the 50–150 ms business-logic delay realistic, or should it be removed/shortened in production?
